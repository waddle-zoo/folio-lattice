# v0 stack research

Date: 2026-09-05

## Goal

Choose the smallest implementation that can prove Folio Lattice's core loop:
store artifacts, connect them in a graph, search and retrieve them through MCP,
write immutable versions, and render untrusted web artifacts without direct
network access or host-origin access.

## Findings

### MCP interface

MCP already has first-class concepts for tools, resources, and standard client
and server transports. v0 should expose the graph and artifact lifecycle as a
small, explicit MCP server contract rather than inventing a provider-specific
agent API. Start with stdio for deterministic local tests and add Streamable
HTTP for the Docker boundary once the handlers are stable.

Sources:

- [MCP transports](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports)
- [MCP Python SDK](https://github.com/modelcontextprotocol/python-sdk)

### Search and grep

SQLite FTS5 provides an in-process full-text index, `MATCH` queries, ranking via
`bm25()`, and snippet/highlight support. That is enough for v0's lexical search
and grep-like retrieval. Semantic/vector search can be an adapter later; it is
not required to prove stable identifiers, chunks, versions, or graph traversal.

Source: [SQLite FTS5](https://www.sqlite.org/fts5.html)

### Graph persistence

The first graph does not need a separate graph database. A normalized SQLite
schema with artifact, version, chunk, node, and edge tables gives transactions,
foreign keys, simple bounded traversal, and one local backup unit. Keep graph
access behind a repository interface so a hosted deployment can replace the
storage adapter without changing MCP semantics.

### Artifact bytes and versions

Store metadata, relationships, versions, blobs, chunks, and provenance in
SQLite. Store bytes under a content-addressed volume keyed by SHA-256. Every
write creates a new version row, even when the blob hash is reused. A version
records its parent, actor/client, timestamp, reason, media type, byte hash, and
source context.

### Web-artifact isolation

An iframe `sandbox` with no `allow-same-origin` is a necessary browser control,
but it is not the whole security boundary. Serve artifacts from a dedicated
origin, apply a restrictive Content Security Policy, and enforce egress at the
container/proxy boundary. The artifact must not receive host cookies or run in
the platform origin. Calls to attached MCPs should go through a parent/platform
bridge that validates an attachment and capability before invoking the MCP.

Sources:

- [HTML iframe sandboxing](https://html.spec.whatwg.org/multipage/iframe-embed-object.html)
- [HTML origin model](https://html.spec.whatwg.org/multipage/browsers.html#origin)

The browser contract should explicitly deny `connect-src` by default. The
platform bridge is the only supported capability path. User-specific MCP
credentials remain out of scope for v0.

### Docker and hosting

Docker Compose is appropriate for the reproducible local topology: one API/MCP
service, one artifact volume, and one testable sandbox boundary. Compose also
has documented patterns for production overrides and remote Docker hosts. Keep
configuration twelve-factor-like and avoid binding development volumes into the
runtime container in production mode.

Sources:

- [Docker Compose](https://docs.docker.com/compose/)
- [Use Compose in production](https://docs.docker.com/compose/how-tos/production/)

## Decision summary

Use Python, SQLite plus FTS5, a content-addressed local artifact volume, an MCP
server with stdio and a Docker HTTP transport, and a separate-origin sandbox
with platform-mediated MCP calls. Do not add a graph database, vector database,
user credential broker, or full UI before the vertical slice proves the core
contracts.
